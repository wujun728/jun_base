### 1.3 核心目标

1. 将 **OA项目**、**项目1**、**SpringBoot3(Geek)项目** 的自定义模块全部融入基座
2. 按 **三层架构** 分类管理：**Plugins（插件）→ Modules（模块）→ Business（业务）**
3. **若依核心6模块原封不动**，保证可持续升级
4. 消除重复模块，统一命名规范

## 二、三层架构设计

### 2.1 架构总览

```
┌─────────────────────────────────────────────────────────────┐
│                      ruoyi-admin（入口）                      │
│              引入 plugins-starter + modules-starter           │
│                  + 业务模块按需引入                            │
├─────────────────────────────────────────────────────────────┤
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────────┐   │
│  │  第一层       │  │  第二层       │  │  第三层           │   │
│  │  ⚙️ plugins   │  │  📦 modules   │  │  🏢 business      │   │
│  │  基础设施插件   │  │  通用中间件    │  │  业务场景模块      │   │
│  │              │  │              │  │                  │   │
│  │  可拔插、可替换 │  │  框架扩展、复用 │  │  业务定制、场景化  │   │
│  │  不依赖业务    │  │  依赖plugins   │  │  依赖modules+插件  │   │
│  └──────────────┘  └──────────────┘  └──────────────────┘   │
├─────────────────────────────────────────────────────────────┤
│              若依核心（ruoyi-common/framework/system）         │
│                    ===== 原封不动 =====                       │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 三层定义

| 层级 | 目录 | 定义 | 特征 | 示例 |
|------|------|------|------|------|
| **Plugins** | `ruoyi-plugins/` | 基础设施能力插件 | 可拔插、可替换、不依赖业务、基于接口实现 | Redis缓存、MinIO存储、RabbitMQ |
| **Modules** | `ruoyi-modules/` | 通用框架扩展模块 | 复用性强、跨项目通用、依赖plugins | 工作流引擎、消息中心、代码生成器 |
| **Business** | `ruoyi-business/` | 业务场景定制模块 | 业务专属、场景化、包含业务逻辑 | 齐兴OA、审批流程、支付场景 |

### 4.2 根 pom.xml 设计

```xml
<modules>
    <!-- ===== 若依核心（不变） ===== -->
    <module>ruoyi-admin</module>
    <module>ruoyi-framework</module>
    <module>ruoyi-system</module>
    <module>ruoyi-quartz</module>
    <module>ruoyi-generator</module>
    <module>ruoyi-common</module>

    <!-- ===== 第一层：基础插件 ===== -->
    <module>ruoyi-plugins</module>

    <!-- ===== 第二层：通用模块 ===== -->
    <module>ruoyi-modules</module>

    <!-- ===== 第三层：业务模块 ===== -->
    <module>ruoyi-business</module>
</modules>
```

**关键设计**：根 pom 只声明 **4个聚合模块**（核心3层），不逐个声明子模块。每个聚合模块内部管理自己的子模块。这样：
- 新增插件/模块/业务时，只需修改对应聚合 POM
- 根 POM 结构稳定，升级若依时不冲突

## 五、重复模块合并策略

### 5.1 Flowable 工作流（M1 — 最高优先级）

| 对比维度 | Geek (geek-module-flowable) | OA (ruoyi-flowable) |
|---------|---------------------------|---------------------|
| Flowable版本 | 7.1.0（适配SB3） | 6.7.2（需升级） |
| 引擎封装 | 基础封装（deploy/expression/listener） | 成熟封装（factory/service） |
| 业务审批 | 无 | 完整（待办/已办/草稿/回收/监控/用印） |
| 数据库迁移 | Liquibase changelog | 手工SQL |

**合并方案**：以 Geek 的 Flowable 7.x 引擎适配为基础 → 融入 OA 的成熟业务逻辑

```
ruoyi-module-flowable/
├── src/main/java/com/ruoyi/flowable/
│   ├── [来自Geek] 引擎核心
│   │   ├── controller/        # FlowDefController, ExpController, ListenerController
│   │   ├── domain/            # SysDeployForm, SysExpression, SysListener, SysTaskForm
│   │   ├── factory/           # FlowServiceFactory (来自OA)
│   │   ├── mapper/            # FlowDeployMapper, SysDeployFormMapper, ...
│   │   └── service/           # IFlowDeployService, IFlowInstanceService, ...
│   │
│   └── [来自OA] 业务审批（迁移到 ruoyi-biz-workflow）
│       └── （不在本模块，见业务层 B2）
│
└── src/main/resources/
    ├── db/changelog/           # 使用Liquibase管理表结构
    └── mapper/flowable/        # Mapper XML
```

## 七、关键技术改造

### 7.1 javax → jakarta（影响 OA + 项目1）

所有未适配的模块需执行：

```powershell
# 批量替换脚本 script/python/javax_to_jakarta.py
# javax.persistence → jakarta.persistence
# javax.servlet → jakarta.servlet
# javax.annotation → jakarta.annotation
# javax.validation → jakarta.validation
# javax.transaction → jakarta.transaction
```

### 7.2 Springfox → Springdoc（影响 OA + 项目1）

```powershell
# 批量替换脚本 script/python/springfox_to_springdoc.py
@Api → @Tag
@ApiOperation → @Operation
@ApiModel → @Schema
@ApiModelProperty → @Schema
@ApiIgnore → @Hidden
swagger.annotations → swagger.v3.oas.annotations
```

### 7.3 Spring Boot 2→3 兼容

| 问题 | 解决方案 |
|------|---------|
| `spring.factories` 废弃 | 改用 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` |
| `@ConfigurationProperties` 扫描 | 添加 `@EnableConfigurationProperties` 或 `@ConfigurationPropertiesScan` |
| Spring Security 5→6 | 基座已处理，业务模块无需改动 |
| `WebMvcConfigurer` 过时方法 | 检查并修复 |

### 7.4 MyBatis / MyBatis-Plus / MyBatis-Flex 共存

| 项目 | ORM | 处理 |
|------|-----|------|
| 基座 | MyBatis 3.0.5 | 保留 |
| 项目1 | MyBatis-Plus 3.4.2 | 升级到 3.5.7+ |
| Geek | MyBatis-Flex 1.11.6 | **不引入**（冲突风险大），Geek模块改用标准MyBatis |

**决策**：统一使用 MyBatis 为主，项目1 可保留 MP 作为独立模块（MP兼容MyBatis）。

## 八、可升级性保障机制

### 8.1 若依核心升级检查清单

当若依发布新版本时，只需：

1. 对比新版 ruoyi-common / ruoyi-framework / ruoyi-system 的 diff
2. 检查是否影响扩展模块的编译（通常不影响，因为扩展模块只 add 不 modify）
3. 更新根 pom 的版本属性
4. `mvn clean install` 验证

### 8.2 隔离原则

```
❌ 不允许：
   - 修改 ruoyi-common/src/main/java/ 下的任何文件
   - 修改 ruoyi-framework 的 SecurityConfig 等核心配置
   - 在 ruoyi-admin 中写业务 Controller

✅ 允许：
   - 在 ruoyi-admin/pom.xml 中添加依赖
   - 在根 pom.xml 的 <modules> 中添加模块
   - 各扩展模块独立编写自己的配置和 Controller
```

### 8.3 配置文件隔离

```
ruoyi-admin/src/main/resources/
├── application.yml              ← [基座] 不追加业务配置
├── application-druid.yml        ← [基座] 不追加业务配置
│
├── application-plugins.yml      ← [新增] 插件层配置（独立文件）
├── application-modules.yml      ← [新增] 模块层配置（独立文件）
└── application-business.yml     ← [新增] 业务层配置（独立文件）
```

通过 `spring.profiles.include: plugins,modules,business` 激活。

## 十一、风险与建议

### 11.1 关键风险

| 风险 | 等级 | 缓解 |
|------|------|------|
| Flowable 6→7 API 变化 | 高 | 在测试分支先验证Geek的Flowable 7.x适配 |
| Vue3前端合并到Vue2 | 高 | Geek前端独立部署为 ruoyi-geek-ui，暂不合入Vue2 |
| MyBatis-Flex与MyBatis冲突 | 中 | Geek模块改用标准MyBatis |
| 大模块编译失败 | 中 | 逐模块编译，及时修错 |
| 菜单ID/权限标识冲突 | 中 | 按ID段严格分配 |
| 三个移动端并存 | 低 | 各自独立部署即可 |

### 11.2 建议

1. **先处理 Plugins 层**（最简单，验证整体架构）
2. **再处理 Modules 层**（合并Flowable是重点）
3. **最后处理 Business 层**（业务模块最多但改造量最小）
4. **Geek的Vue3前端保持独立**，不要强行并入Vue2的 ruoyi-ui
5. **分阶段提交代码**，每完成一层就编译通过，便于回溯
6. **先不做Liquibase**，继续用手工SQL，降低复杂度
